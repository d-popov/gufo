## Operating rules
- **Python changes need `systemctl --user restart gufo-monitor.service`.** Static files are read from disk per request,
  so a new `chat.js` can be served by an old process that lacks the new route/whitelist. That mismatch caused the
  "no models / no Project UI" reports. New static scripts must be added to `STATIC_FILES` in `gufo-monitor.py`, to
  `chat.html` (order matters) and to the whitelist/order assertions in `monitor_test.py`.
- Test pattern: scratch monitor + fake Gufo (`/v1/models`, `/ready`, SSE `/v1/chat/completions`) on private ports, a
  throwaway `--stats-file`/`--chat-store`, then drive Chromium with the browser tool and check DOM text only (no
  screenshots without asking, per user rules). Node tests load the browser scripts with `vm.runInNewContext` (compare
  arrays via JSON; cross-realm `deepEqual` fails).
- Commit style: Conventional Commits, one-line messages. Do not touch live services without being asked.

## Features built (all committed on `local`, all live after the last restart)
- **Projects**: folder of chats with *guidelines* (user-written, "Draft guidelines" via the model) and *memory*
  (model-maintained after a reply goes idle 60 s, on leaving a chat, or on button; a chat keeps the memory it started
  with so prompts stay cache-friendly). Export/Import as one `.md` (`# Guidelines` / `# Memory`). `static/projects.js`.
- **Local store**: IndexedDB per account (`gufo-chat`, `gufo-chat-<owner>`), unlimited history, list shows 200 newest per
  project; legacy localStorage histories migrated only into the admin DB and only deleted after a persistent commit
  (`chatstore.js`, regression test `chatstore_test.js`).
- **Server-side sync** (`b7525015`): `ChatStore` SQLite per owner (admin or portal user), revisions + tombstones (90 d),
  quotas (256 MiB, 20k items, chat 4 MiB, project 256 KiB), routes `GET /api/chat/sync?since=`,
  `PUT/DELETE /api/chat/items/{chat|project}/ID`; later `updated` wins (device clock; chats use `modified`). Client
  engine `chatsync.js` (push after 1.5 s, pull on open/visible/online/45 s, skips an item while a reply is writing into
  it). `/api/chat/models` returns `owner` and `sync`; **a missing owner (older monitor) fails closed: in-memory store,
  never the admin DB.** The admin can read `chats.sqlite` (stated in README).
- **Resumable replies** (`6a28052d`): replies are generated by `ChatRuns` threads independent of the browser; the page
  reattaches at `GET /api/chat/runs/ID?from=N` after backgrounding; `POST .../cancel`; orphan cancel after 180 s, finished
  runs kept 600 s in memory. Verified with a simulated background in Chromium, not on a real phone.
- **Steering** (`f3cf09ce`): a message sent while a reply is writing is queued (chip above the box); it interrupts the
  current model call immediately (partial text kept) or waits for running tools, then continues as a new answer below.
  Stop on an empty box ends the reply and restores undelivered messages. Verified in Chromium against a fake model only.
- **Media**: `find_media` tool (Wikimedia Commons only; model never supplies URLs); CSP for `/chat` allows
  `upload.wikimedia.org`/`thumb.wikimedia.org` images and `upload.wikimedia.org` media; videos use the nearest-480p VP9
  rendition. Playback verified by keyboard (Space) in Chromium; a synthetic mouse click did not start playback (harness
  limit); iOS < 17.4 cannot play VP9 inline.
- **Mobile layout** (`chat.css` media query <= 640 px): one-row header, compact toolbar/composer, project panel overlay
  with a sticky Done button. Measured in a 375 px viewport; not tried on a real phone.
- **Model list robustness**: `_poll_info` keeps the last list on a refused/failed `/v1/models` and re-polls every poll
  while empty; the chat loads models first, retries every 5 s, and degrades if `projects.js`/`chatstore.js` are missing.
- Default chat model via `--chat-model`; the user's pick is remembered in localStorage.
- **Private library** (not yet committed or restarted into the live service): `library.py` (Markdown pages + SQLite FTS5/BM25
  index + link graph, ingest/digest jobs, auto-linking both ways), `library_mcp.py` (stateless Streamable HTTP MCP: `search_library`,
  `read_library`, `list_library`), routes `/api/library/*` and `POST /mcp` in `gufo-monitor.py`, admin panel `static/libraryadmin.js`
  (monitor page), chat tools `static/librarytools.js` (admin only, via `POST /api/library/call`). `--library-dir`, default
  `~/.config/gufo-monitor/library`. The read-only **library token** (`glib-…`, HMAC of the admin token) is the only credential `/mcp`
  accepts; the admin token and inference keys are never given to MCP clients. Tests: `tests/tools/library_test.py`,
  `librarytools_test.js`. Verified on a scratch monitor (port 18097, not the live service) against the real Gufo and
  `qwen3.8-flash-next-sub`: a Markdown text and a text-layer PDF digested in ~13 s each (summary, aliases, tags, 5 concept pages
  each), cross-links in both directions, a third document linking back into an older page, and a real chat that searched,
  read and cited library pages by slug (15 tool calls). A scanned PDF and a very long document were not tried. PDF needs `pdftotext`.
- Earlier work in the same folder: Python (Pyodide) and web tools, API-key admin, credits portal.

## Known gaps / ideas
- Sync conflict rule uses client clocks; no merge of two edits to one chat. Portal-user sync was tested with a stubbed
  user lookup, not a real signed-in portal session. No UI indicator of sync state/errors beyond the status line.
- Steered/interrupted calls lose their usage numbers (token totals slightly low); each interruption counts toward the
  6-call tool round limit.
- Memory updates and draft-guidelines are billed requests for portal users and are not in the chat total.
- Chat sync stores messages only; image bytes are intentionally never stored.
- Possible: server-pushed sync (SSE) instead of 45 s polling; more media sources (Openverse timed out from the shell);
  per-user storage view/delete in admin; mobile verification on a real device.
- Library: no OCR for scanned PDFs; concepts come from the first 6x20k characters of a document; web tools and library tools can be
  ticked together (the system note forbids copying library text into web queries, nothing enforces it); portal users have no library.
